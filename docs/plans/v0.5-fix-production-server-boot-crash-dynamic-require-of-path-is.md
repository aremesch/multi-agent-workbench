# Fix: production server boot crash — `Dynamic require of "path" is not supported` (jsdom)

## Context

The production `maw.service` crashes at boot:

```
Error: Dynamic require of "path" is not supported
    at file:///home/maw/maw/build/server.js:13:9
    at node_modules/.pnpm/jsdom@29.1.1_.../jsdom/lib/api.js (build/server.js:306448:16)
    at __require2 (build/server.js:19:51)
```

The server logs through startup (migrations, push, cli-adapters, supervisor
reattach, queue scheduler) and then dies as the ESM module graph finishes
evaluating. The service is completely unbootable in production.

### Why it happens

- The root entry [server.js](server.js) imports `bootstrap` from
  `src/lib/server/bootstrap.ts`; that graph transitively reaches
  [src/lib/server/plans/agentPlans.ts:42](src/lib/server/plans/agentPlans.ts:42),
  which eagerly imports `isomorphic-dompurify` (a **prod** dependency,
  [package.json:72](package.json)) to sanitize markdown-rendered plan HTML.
- `isomorphic-dompurify` eagerly imports **jsdom** at module top-level
  (`var window = new JSDOM(...)` runs on import) — the `jsdom@29.1.1` in the
  stack trace.
- The production server is bundled by the custom esbuild script
  [scripts/bundle-server.mjs](scripts/bundle-server.mjs), which inlines all of
  `src/lib/server/**` into one ESM `build/server.js` using a **hand-curated
  `external` allowlist**. `isomorphic-dompurify` / `jsdom` / `dompurify` are
  not on that list, so jsdom is bundled in. jsdom is CommonJS and calls
  `require()` dynamically; esbuild rewrites those as a `__require2` shim that
  throws under ESM, at boot.

### Why this recurs (the real problem)

This is the **third** instance of the same bug class already documented in that
file — `simple-git` (`Dynamic require of "fs"`) and `playwright` (chromium-bidi
dynamic require) were each fixed by manually adding them to the allowlist
*after* they bit. The bundler bundles by default and externalizes only an
opt-in list, so every CJS-with-dynamic-`require` package must be discovered
(usually via a prod crash) and added by hand. Two things make it reach prod:

1. **Opt-in allowlist** — new offending deps aren't excluded until someone
   notices.
2. **CI never boots the bundle** — [unit.yml](.github/workflows/unit.yml) runs
   vitest against *source*; [e2e.yml](.github/workflows/e2e.yml) runs Playwright
   against dev/preview. Neither runs `pnpm build` + boots `build/server.js`, so
   bundle-only crashes are invisible until deploy.

### Intended outcome

`build/server.js` boots cleanly, plan markdown still renders/sanitizes exactly
as before, and this bug class can no longer reach production.

## Recommended fix (structural — fixes jsdom **and** prevents recurrence)

### 1. Externalize all npm packages in the esbuild bundle

In [scripts/bundle-server.mjs](scripts/bundle-server.mjs), replace the
hand-curated `external: [...]` array with esbuild's
[`packages: 'external'`](https://esbuild.github.io/api/#packages) option.
That leaves every bare-specifier import (anything from `node_modules`) as a
runtime import and bundles only our own source (relative imports + the
`$shared` alias). No npm package — CJS, ESM, dynamic-require, or otherwise —
can hit the `__require2` shim again.

```js
await build({
  entryPoints: ['server.js'],
  outfile: 'build/server.js',
  bundle: true,
  platform: 'node',
  format: 'esm',
  target: 'node20',
  packages: 'external',        // ← externalize everything in node_modules
  plugins: [handlerRewritePlugin],
  alias: { $shared: resolve('src/lib/shared') },
  treeShaking: true,
  sourcemap: true,
  minify: false,
  logLevel: 'warning',
  banner: { js: '// Multi-Agent Workbench — bundled production server entry\n' },
});
```

Why this is safe and correct:
- It **subsumes** every entry currently in the `external` array, including the
  `better-auth` / `zod@4` sub-tree nuance — externalizing was always the *safe*
  direction (the existing comment warns against *inlining* zod, never against
  externalizing). Sub-path specifiers like `better-auth/cookies` are covered
  too (they're bare specifiers).
- `node:*` builtins stay external (platform node). The relative
  `./build/handler.js` import is still handled by `handlerRewritePlugin`, and
  `src/lib/server/**` + `$shared` stay bundled.
- **Deployment unchanged:** `node_modules` is already required at runtime
  (every existing external proves this); every server-runtime import is a prod
  `dependency`, so `pnpm install --prod` provides them.
- esbuild ^0.28 ([package.json:41](package.json)) supports `packages:
  'external'`.

The previously planned minimal change (adding `isomorphic-dompurify`/`jsdom`/
`dompurify` to the allowlist) becomes unnecessary — it's a strict subset of
this.

### 2. Boot the bundle in CI (regression backstop)

Add a build-and-boot smoke step so any future bundling regression fails at PR
time instead of in production. Either a new workflow
(`.github/workflows/build-smoke.yml`) or a job appended to
[unit.yml](.github/workflows/unit.yml):

- `pnpm install --frozen-lockfile`
- `pnpm build`
- boot `build/server.js` in an isolated env so the supervisor reattaches **0**
  agents and touches no real state — scratch `dataDir` + a dedicated
  `MAW_TMUX_SOCKET` (per the project's test-isolation convention) — wait for
  the `queue scheduler: started` ready line, then kill it. **Fail** if the
  process exits early or emits `Dynamic require` / any uncaught error during
  boot.

A small Node/bash harness (e.g. `scripts/smoke-boot.mjs`) that spawns the
server, scans stdout for the ready line vs. the error signature, enforces a
timeout, and exits non-zero on failure is the cleanest form and is reusable
locally.

### Files to modify

- [scripts/bundle-server.mjs](scripts/bundle-server.mjs) — swap `external: [...]`
  for `packages: 'external'` (and delete the now-dead array + its comments).
- `.github/workflows/` — add the build-and-boot smoke job (new file or a job in
  `unit.yml`).
- (new) `scripts/smoke-boot.mjs` — optional boot harness used by the CI job.

### Considered but not chosen

- **Minimal allowlist addition** (`isomorphic-dompurify` + `jsdom` +
  `dompurify` into `external`): smallest possible diff and fully fixes *this*
  crash, but leaves the opt-in design intact — the next CJS dynamic-require dep
  will do this again. Acceptable as a conservative fallback if the structural
  change is deemed too broad for a hotfix; superseded by `packages: 'external'`.
- **Replace `isomorphic-dompurify`/jsdom with a DOM-free sanitizer**
  (e.g. `sanitize-html`): sheds the heavy jsdom dependency, but a sanitizer is
  a security boundary — a different engine has different default rules and
  edge-case (mutation-XSS) behavior, so it requires re-validating that it
  blocks everything the current `FORBID_TAGS`/`FORBID_ATTR` config blocks.
  Out of scope for a boot-crash fix; worth a separate, tested follow-up if
  dependency weight matters.
- **Lazy/dynamic `import()` of the sanitizer**: does **not** fix it. The crash
  is that jsdom is *bundled* (esbuild's `__require2` shim throws whenever the
  code runs), not *when* it's imported. Lazy-loading only moves the crash from
  boot to the first plan render — arguably worse (boots "healthy", 500s on
  first use). Externalizing is the actual fix.

   `renderPlanMarkdownToHtml()` / `agentPlans.ts` still sanitize correctly via

   bundle regressed (verify by temporarily reintroducing the bug locally).
