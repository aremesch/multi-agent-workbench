# Symphony Spec → MAW Integration

## Context

The user shared the Symphony Service Specification (draft v1) — a long-running
daemon that polls Linear, creates per-issue workspaces, runs Codex coding-agent
sessions, supports retry/backoff + stall detection + lifecycle hooks, and reads
its policy from a repo-owned `WORKFLOW.md` (YAML front matter + Markdown body).

The user signed off on **all four phases** below and chose **`.maw/workflow.md`**
as the single, repo-owned config file (Symphony-style YAML front matter +
Markdown body). That choice unifies the integration around one file: hooks +
tracker + per-repo agent policy live together; the Markdown body becomes the
auto-pilot prompt template (Phase 4).

What MAW *has today* that Symphony covers under different names:

- **Programmable spawn**: [`AgentSupervisor.spawn()`](src/lib/server/agents/AgentSupervisor.ts:455) ← Symphony's "dispatch worker"
- **Per-issue workspace**: [`WorktreeManager.create()`](src/lib/server/git/WorktreeManager.ts:69) with `base_sha` capture
- **Reattach on boot**: tmux session liveness check during supervisor `init()`
- **Hot-reloaded adapter config**: `cli-adapters/*.jsonc` via chokidar
- **Repo-owned config reader**: [`agentPlans.ts`](src/lib/server/plans/agentPlans.ts) reading `.claude/settings.json#plansDirectory`
- **Reaper loop**: 5-s setInterval at [`bootstrap.ts:150`](src/lib/server/bootstrap.ts:150)
- **Per-agent hooks**: claude-code `Notification` / `PreToolUse` (loopback bearer token, [`api/internal/claude-hook`](src/routes/api/internal/claude-hook/+server.ts))

What MAW *lacks* (and Phases 1–4 add):

- Workspace lifecycle hooks
- Stall detection + concurrency caps
- Retry / auto-resume after exit
- Tracker (Linear) integration / poll loop
- Active-run reconciliation against tracker state
- Repo-owned policy file with hot-reload

## Symphony parts deliberately skipped

| Symphony concept                                   | Why skip                                                                                                                            |
| -------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| `linear_graphql` agent tool extension              | Use a Linear MCP server; don't bake tracker auth into the agent's toolchain.                                                        |
| Codex JSON-RPC app-server protocol                 | MAW runs codex via PTY uniformly with claude-code/gemini. Reimplementing JSON-RPC inside MAW splits transport without benefit.      |
| Strict Liquid prompt template engine               | MAW's `task.body` is user-typed; for Phase 4, simple `{{var}}` substitution (already used by adapter `initialInput`) is sufficient. |
| Headless daemon mode (no UI)                       | MAW is UI-first. A headless mode would split the product. Auto-pilot lands as a feature, not a separate runtime.                    |
| `agent.max_concurrent_agents_by_state`             | MAW has no tracker state to key on outside Phase 4; even there, per-cli_kind + per-repo caps cover the same need more naturally.    |
| Per-issue continuation across multiple turns on a single live thread | MAW's adapters are PTY-driven, not JSON-RPC. Phase 3 captures the *intent* (auto-resume) without reimplementing thread/turn semantics. |

## The shared config file: `.maw/workflow.md`

Symphony-shape, YAML front matter + Markdown body. One file owns *all* repo
policy across the four phases:

```markdown
---
# ---- Phase 1: Hooks ----
hooks:
  afterCreate: |
    pnpm install --frozen-lockfile
  beforeRun: null
  afterRun: null
  beforeRemove: null
  timeoutMs: 60000

# ---- Phase 2: Runtime limits (per-repo override of user_settings) ----
runtime:
  stallTimeoutMs: 300000          # 0 = disabled

# ---- Phase 3: Auto-resume defaults ----
autoResume:
  defaultMaxAttempts: 0           # 0 = off; per-spawn flag still wins

# ---- Phase 4: Tracker auto-pilot ----
tracker:
  kind: linear                     # only `linear` shipped initially
  endpoint: https://api.linear.app/graphql
  apiKeyEnv: LINEAR_API_KEY        # legacy fallback; user-scoped key takes precedence
  projectSlug: ABC123
  activeStates: [Todo, In Progress]
  terminalStates: [Done, Cancelled, Closed, Duplicate]
polling:
  intervalMs: 30000
agent:
  cliKind: claude-code             # which adapter auto-pilot uses
  roleId: rol_default              # required when tracker is enabled
  maxConcurrent: 5
---

# Optional Markdown body — used only by Phase 4 auto-pilot

When the auto-pilot dispatches an agent for an issue, this body is rendered as
the prompt template (with simple `{{issue.title}}`, `{{issue.identifier}}`,
`{{issue.description}}`, `{{attempt}}` substitution) and becomes `task.body` for
the spawn. Manual spawns ignore it.
```

**Parsing**: zod-validated front matter, missing keys default cleanly. Reader
mirrors [`agentPlans.ts`](src/lib/server/plans/agentPlans.ts) (path validation,
no traversal, fallback default). Hot-reload via chokidar in Phase 4 only (per
spawn / per tick read-on-demand is sufficient for Phases 1–3).

**New dep**: `yaml` (eemeli/yaml on npm — well-maintained, ~70 kb,
license-clean). No `js-yaml` (heavier, older). Add to `dependencies`.

**Validation errors**: surface to spawn UI as a friendly message
("`.maw/workflow.md` invalid at `hooks.timeoutMs`: expected positive integer").
Don't crash the supervisor; fall back to behaviour-as-if-missing.

**Co-existence with Symphony's spec**: deviates only where MAW already has a
better surface — `agent.maxConcurrent` is per-repo (overrides the per-user cap
from Phase 2), `agent.cliKind` replaces Symphony's `codex.command` (MAW's
adapter system already covers that), `agent.roleId` is MAW-specific. Everything
else mirrors Symphony's keys 1:1 so a team that knows Symphony can read this
file and understand it.

## Phase 1 — Workspace lifecycle hooks

**Goal**: Per-repo automation versioned with the code (e.g. `pnpm install`
after worktree create, `pnpm test:smoke` before agent runs).

**Behaviour**:

- `hooks.afterCreate`: runs only when the worktree was just created (not reused). Failure aborts spawn.
- `hooks.beforeRun`: runs after worktree prep, before tmux session create. Failure aborts spawn.
- `hooks.afterRun`: runs after `finishAsExited` and *before* `snapshotAgentCommits`. Failure logged, ignored.
- `hooks.beforeRemove`: runs before worktree deletion. Failure logged, ignored.
- All hooks: `bash -lc <script>` in worktree cwd; per-hook timeout (`hooks.timeoutMs`, default 60 s).
- Hook output piped to a system-tagged terminal-log line (`[maw-hook] afterCreate: …`) so the user sees it in xterm.

**Files**:

- new: `src/lib/server/workflow/workflowFile.ts` — reads + zod-validates `<repo>/.maw/workflow.md`. Returns `{ frontMatter, body }`.
- new: `src/lib/server/workflow/runHook.ts` — exec wrapper (timeout, cwd, env, piping output to runtime's onChunk).
- new: `src/lib/server/workflow/workflowFile.test.ts` — vitest cases for the reader (valid / missing / malformed YAML / missing front matter / unknown keys / path traversal).
- new: `src/lib/server/workflow/runHook.test.ts` — vitest cases for the runner (success / non-zero exit / timeout / no-such-script).
- modify: [`WorktreeManager.create()`](src/lib/server/git/WorktreeManager.ts:69-105) — call `runHook(workflow.hooks.afterCreate, …)` only when worktree was just created.
- modify: [`AgentSupervisor.spawn()`](src/lib/server/agents/AgentSupervisor.ts:455-643) — call `runHook(...beforeRun)` after worktree prep, before `Tmux.newSession()`. On failure: roll back DB row, abort, surface to form.
- modify: [`AgentSupervisor.finishAsExited()`](src/lib/server/agents/AgentSupervisor.ts:383-443) — call `runHook(...afterRun)` *before* `snapshotAgentCommits()`.
- modify: worktree delete path (search for "worktree remove" / "rmdir") — call `runHook(...beforeRemove)`.
- new dep: `yaml` (npm).
- new e2e spec: `e2e/workflow-hooks.spec.ts` — shell agent spawned against a fresh repo with `afterCreate: "echo HOOK > .maw-hook-marker"`, asserts the marker exists; respawn → marker not recreated; failing `beforeRun` aborts spawn with friendly error in form.

**Out of scope**:

- No UI editor (file lives in repo, edited like any source file).
- `beforeTurn` per-turn hook (would only matter with Phase 3 auto-resume; revisit if Phase 3 doesn't cover the need).

## Phase 2 — Stall detection + concurrency caps

**Goal**: Catch hung agents, prevent runaway spawns.

**Stall detection**:

- New `user_settings` key `agent.stallTimeoutMs` (default `300000` = 5 min; `0` = disabled).
- Per-repo override via `runtime.stallTimeoutMs` in `.maw/workflow.md` (wins over user_settings).
- Extend the reaper at [`bootstrap.ts:150-154`](src/lib/server/bootstrap.ts:150) (already runs every 5 s). For each runtime, compute `Date.now() - last_attention_at`; if `> stallTimeoutMs` and `stallTimeoutMs > 0`, call `supervisor.kill(agentId)` with reason `stalled`.
- Surface as toast via existing AlertBus: "Agent ABC stalled — 5 min of silence". Reuses the alert pipeline from [`v0.2-rich-input-notifications.md`](docs/plans/v0.2-rich-input-notifications.md).
- No new column needed; the existing alert payload + `crashed` status flip is enough.

**Concurrency caps**:

- New `user_settings` keys:
  - `agent.maxConcurrent` (default `0` = unlimited, applies user-wide)
  - `agent.maxConcurrentByKind` (map of `cli_kind` → positive integer, default `{}`)
- Per-repo override via `agent.maxConcurrent` in `.maw/workflow.md` (wins over user_settings; manual spawns into that repo subject to the repo cap).
- Preflight check in `AgentSupervisor.spawn()` *before* DB insert; if cap hit, throw `SpawnConcurrencyError` the form action renders as `error.spawn.concurrencyCap` (i18n: EN/DE/ES/FR).
- In-memory check is enough (single-process MAW). No DB-level enforcement.

**Files**:

- modify: [`src/lib/server/bootstrap.ts:150-154`](src/lib/server/bootstrap.ts:150) — extend reaper with stall check; reads workflow file (read-on-demand, cached per-tick) and falls back to user_settings.
- modify: [`AgentSupervisor.spawn()`](src/lib/server/agents/AgentSupervisor.ts:455) — preflight cap check.
- new: `src/lib/server/agents/concurrencyCheck.ts` — extracted helper, easy to unit-test.
- modify: `src/routes/settings/+page.{svelte,server.ts}` — new section *Agent runtime limits* (stall timeout slider + per-kind caps).
- modify i18n bundles (EN/DE/ES/FR).
- new vitest cases for cap preflight + stall reaper logic.
- new e2e spec — set `maxConcurrent=1`, spawn 2 shell agents → 2nd rejected with the cap message; idle agent past stall timeout → killed + alert toast visible.

**Out of scope**:

- No per-repo cap UI (config-only via `workflow.md`).
- Stall detection only kills; auto-respawn is Phase 3.

## Phase 3 — Auto-resume on exit

**Goal**: Long tasks (claude-code with `--continue`, codex multi-step) keep
working without manual respawn.

**Per-spawn flag**: New checkbox in spawn dialog *"Auto-resume until task
complete"* (default off). Stored on `agents.auto_resume_max` (integer, `0` =
off). Default value comes from `autoResume.defaultMaxAttempts` in
`.maw/workflow.md` (per-repo); user can still override per spawn.

**On `finishAsExited`**:

- Eligible: `auto_resume_max > 0` AND `auto_resume_remaining > 0` AND exit was clean (status `exited`, *not* `crashed`, *not* `stalled`).
- If eligible:
  - Decrement `auto_resume_remaining` (persisted before respawn).
  - Re-spawn into the **same worktree** (same `repoPath`, `worktreePath`, `baseSha`, `current_task_id`).
  - On the new tmux session, after the existing 1500 ms warmup delay, send `adapter.spawn.continuationInput` via the existing `send_keys` path — no new transport.
  - For claude-code: also inject `--continue` flag (or `--resume <cli_session_id>` if available) via a new `adapter.spawn.continuationArgs` array.
- Surface as system message: `[maw] Auto-resuming agent (attempt 2 of 3)`.
- **Loop guard**: never auto-resume on `crashed` / `stalled` / `tracker_terminal` (Phase 4); always decrement; hard-stop at 0.

**Adapter JSONC additions** (validated in [`adapter.config.schema.ts`](src/lib/server/agents/adapters/adapter.config.schema.ts)):

- `spawn.continuationInput` (string, optional)
- `spawn.continuationArgs` (string[], optional)
- Examples to ship:
  - `claude-code.jsonc`: `continuationArgs: ["--continue"]`, `continuationInput: ""` (the flag does the work)
  - `codex.jsonc`: `continuationInput: "resume"` (or whatever bare codex CLI accepts)
  - `gemini.jsonc`: `continuationInput: "continue"`
  - `shell.jsonc`: not set (auto-resume meaningless for the smoke adapter)

**Files**:

- new migration `009_agent_auto_resume.sql`:
  ```sql
  ALTER TABLE agents ADD COLUMN auto_resume_max INTEGER NOT NULL DEFAULT 0;
  ALTER TABLE agents ADD COLUMN auto_resume_remaining INTEGER NOT NULL DEFAULT 0;
  ```
- modify: [`AgentSupervisor.finishAsExited()`](src/lib/server/agents/AgentSupervisor.ts:383-443) — chain to `spawn()` if eligible, with a re-entry guard so `auto_resume_remaining < 0` is impossible (atomic DB decrement-then-respawn).
- modify: [`adapter.config.schema.ts`](src/lib/server/agents/adapters/adapter.config.schema.ts) — add the two new fields.
- modify: `cli-adapters/claude-code.jsonc`, `codex.jsonc`, `gemini.jsonc`.
- modify: `src/routes/agents/new/+page.svelte` — checkbox + max-attempts number input. Default reflects `autoResume.defaultMaxAttempts` from workflow file.
- modify: `src/routes/agents/new/+page.server.ts` — pass through to `supervisor.spawn`.
- new vitest cases for finishAsExited auto-resume branch (eligible / not-eligible / loop-guard / per-repo default override).
- new e2e spec — shell adapter that exits cleanly, max=2 → exactly 2 resumes; force-crash variant → no resume.

**Out of scope**:

- No tracker-driven termination (that's Phase 4 — auto-resume respects Phase 4's `tracker_terminal` reason via the loop guard).
- No manual "resume now" button (could come later).

## Phase 4 — Tracker auto-pilot (Linear)

**Goal**: Symphony's headline use case — poll Linear, dispatch agents per
issue, reconcile state.

**Per-repo enablement**:

- `repos.auto_pilot_enabled` BOOLEAN DEFAULT FALSE (new column via migration).
- UI toggle at `/repos/[id]/auto-pilot` — when toggled on, MAW validates `<repo>/.maw/workflow.md` has `tracker.*` populated and either `LINEAR_API_KEY` is set globally OR a user-scoped tracker key exists.
- User-scoped Linear key: stored at `user_settings` key `autoPilot.<repoId>.linearApiKey` (encrypted at rest if MAW gains a key-blob facility; for now plain JSON, gated by user-scoped access).

**Polling**:

- New `src/lib/server/autoPilot/index.ts` — driver. On supervisor `init()` and on `auto_pilot_enabled` toggle, start a `setInterval(workflow.polling.intervalMs)` per enabled repo. Stop / restart on toggle changes or `workflow.md` change (chokidar watcher in this module).
- Each tick:
  1. **Reconcile** running auto-pilot agents (Symphony §8.5) — fetch tracker states for the agents' issues, kill any whose state is now terminal (with reason `tracker_terminal`).
  2. **Validate** `workflow.md` (skip dispatch on errors, keep reconciliation alive).
  3. **Fetch candidates** — Linear GraphQL with `project: { slugId: { eq: $slug } }`, paginated (page size 50, 30 s timeout per Symphony §11.2).
  4. **Filter** — active state, not terminal, not already in `auto_pilot_runs` for this repo, blocker rule for `Todo` (skip if any non-terminal blocker).
  5. **Sort** — priority asc, created_at oldest first, identifier lex tie-break.
  6. **Dispatch** — for each eligible issue while concurrency slots remain: `WorktreeManager.create()` (slug = sanitized issue identifier), render Markdown body as prompt with `{{issue.*}}` + `{{attempt}}` substitution, `supervisor.spawn()` with `task.body = rendered`, insert `auto_pilot_runs` row, store `external_id` for dedupe.

**Reconciliation** (Symphony §8.5 part B):

- Reuses the existing 5-s reaper for stall detection.
- The auto-pilot tick handles tracker-state reconciliation; transition to `terminal` triggers `supervisor.kill(agentId, 'tracker_terminal')`.
- Phase 3 auto-resume respects `tracker_terminal` via the loop guard.

**Continuation across multiple worker exits** (Symphony §7.1 nuance):

- After a clean agent exit on an active issue, the auto-pilot tick re-checks the issue state. If still active → mark `auto_pilot_runs.status = 'pending_continuation'`; next tick re-dispatches into the *same* worktree. This is Phase 3 auto-resume's machinery, just driven by the auto-pilot tick instead of `finishAsExited` directly.
- Cap by `agent.maxConcurrent` from `workflow.md`.

**Files**:

- new migration `010_auto_pilot.sql`:
  ```sql
  ALTER TABLE repos ADD COLUMN auto_pilot_enabled INTEGER NOT NULL DEFAULT 0;
  CREATE TABLE auto_pilot_runs (
    id TEXT PRIMARY KEY,
    repo_id TEXT NOT NULL REFERENCES repos(id) ON DELETE CASCADE,
    tracker_kind TEXT NOT NULL,
    external_id TEXT NOT NULL,             -- Linear issue id
    external_identifier TEXT NOT NULL,     -- e.g. ABC-123
    agent_id TEXT REFERENCES agents(id) ON DELETE SET NULL,
    status TEXT NOT NULL,                  -- pending|running|exited|tracker_terminal|failed
    attempt INTEGER NOT NULL DEFAULT 1,
    last_error TEXT,
    created_at INTEGER NOT NULL,
    updated_at INTEGER NOT NULL,
    UNIQUE(repo_id, tracker_kind, external_id)
  );
  ```
- new: `src/lib/server/autoPilot/index.ts` — driver
- new: `src/lib/server/autoPilot/trackers/linear.ts` — GraphQL client, payload normalization to MAW's issue model
- new: `src/lib/server/autoPilot/dispatch.ts` — eligibility, sort, dispatch
- new: `src/lib/server/autoPilot/reconciler.ts` — tracker state refresh + kill logic
- new: `src/lib/server/autoPilot/promptTemplate.ts` — render workflow body with `{{issue.*}}` / `{{attempt}}` (simple `{{var}}` substitution, no Liquid)
- new: `src/routes/repos/[id]/auto-pilot/+page.{svelte,server.ts}` — enable toggle, paste tracker token, show `auto_pilot_runs` table (last poll, dispatched issues, kill reasons)
- new dep: nothing additional (use built-in `fetch` for Linear GraphQL)
- new env: `LINEAR_API_KEY` (fallback only; preferred path is user-scoped key)
- new docs/plans entry once Phase 4 starts: `v0.4-auto-pilot.md`
- new e2e spec — mocked Linear GraphQL endpoint with 2 active issues; toggle auto-pilot on; poll once → 2 agents dispatched into 2 worktrees; flip 1 issue to terminal in mock → reconciler kills that agent only; re-poll → no duplicate dispatch (deduped by `auto_pilot_runs`).

**Out of scope**:

- Multi-tracker (GitHub Issues, Jira, etc.) — Linear only initially. Tracker adapter pattern leaves room.
- Symphony's `linear_graphql` agent tool extension — use Linear MCP if needed.
- Web push notifications when auto-pilot dispatches/kills — could come later via existing alert pipeline.
