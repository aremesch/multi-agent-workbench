# Mass agent-death incident — investigation & remediation

## Context

On the production LXC container (PVE CTID 112, host `pve`, container `maw`),
**six** running claude-code agents died simultaneously at **22:03:15** on
2026-05-21 while at least one was actively working. This is the second time the
symptom has occurred. The user suspected the kernel OOM killer; the evidence
below **refutes that hypothesis** but does not yet identify the true cause.
This document captures what we know, what we can rule out, and what to do
next — both to confirm the cause when it next recurs and to harden MAW so
this is observable and survivable.

## Evidence collected so far

### Timeline (UTC+2)
- **22:03:15** — In a single second, the maw service journal emits 11 log
  lines: commit snapshots for 6 agents (4 `(range)`, 2 `(committer)` with
  0 commits) plus one new agent spawn (`01KS62555JKY44SV37Z0VEZVK3`, the
  polyrepo task). All commit-snapshot lines come from `finishAsExited()` at
  [AgentSupervisor.ts:452-466](src/lib/server/agents/AgentSupervisor.ts:452) —
  i.e. **all six were detected as having lost their tmux session in the same
  reap pass**.
- **22:03:16 → now (22:18+)** — Complete silence in `journalctl --user-unit
  maw`. No further reap output (correct, because the runtime map is now
  empty), no errors, no shutdown signals.
- **Proxmox dashboard** for CT112 shows:
  - Container memory drops from ~2.5 GiB → ~0.5 GiB at 22:03 (processes
    exited, freeing memory — this is the *consequence* of the deaths).
  - CPU pressure-stall spike to ~4 % at 22:03.
  - Heavy disk reads tapering off after 22:03.
  - Heavy outgoing network ending ~22:05.
  - **Peak memory across the entire hour stayed below ~3 GiB of 8 GiB.**

### What's still alive
- `maw.service` (PID 60839) — alive, `State: S (sleeping)`, RSS 222 MiB.
  HTTP responds in 3 ms.
- `maw-tmux.service` (PID 247) — alive since 2026-05-19. Cgroup memory now
  1.1 GiB, **almost entirely `file` (page cache) — only 7 MiB anon**.
- 2 orphan `sh -c "cat >> /tmp/maw-fifos/fifo-test-<pid>"` processes (PIDs
  163123 from 21:48 and 163748 from 21:51), parented to tmux. They are
  leftover from `fifo-test-*` probes that never appear elsewhere in the
  production source — only in the test harness
  ([FifoStreamer.test.ts via `maw-fifo-test-*`](src/lib/server/agents/FifoStreamer.ts)).
  These survived precisely because they have ~0 memory and ~0 CPU.
- One orphan FIFO file `/tmp/maw-fifos/fifo-01KS62555JKY44SV37Z0VEZVK3` from
  the spawn-in-progress agent.

### What's gone
- All `maw-agent-*` tmux sessions (`tmux -L maw list-sessions` returns
  empty).
- All claude-code child processes.

## Hypotheses

### 1. Kernel OOM killer — **REFUTED (host + container)**
- Every readable cgroup `memory.events` (root, user-slice, user@,
  app.slice, maw.service, maw-tmux.service) shows `oom_kill 0`.
- The **host-side LXC cgroup** `/sys/fs/cgroup/lxc/112/memory.events` also
  shows `oom_kill 0` (the one counter we couldn't see from inside).
- `journalctl -k --since "2026-05-21 22:00" --until "2026-05-21 22:10"` on
  the PVE host: **no entries** — the kernel logged nothing at all.
- `pct config 112` confirms `memory: 8192`, `swap: 0` (no swap available).
- Peak container memory was ~30 % of the 8 GiB limit.
- The dashboard memory drop is the *result* of processes exiting cleanly,
  not the cause.

### 2. Bulk-kill from MAW code — **REFUTED**
- The only `supervisor.kill()` callers are the per-agent stop route
  ([src/routes/api/agents/[id]/stop/+server.ts](src/routes/api/agents/[id]/stop/+server.ts))
  and `Scheduler.cancelEntry()`
  ([src/lib/server/queue/Scheduler.ts:175](src/lib/server/queue/Scheduler.ts:175)).
  Neither is a bulk path.
- No `tmux kill-server` or "stop all" endpoint exists in the codebase.

### 3. Scheduled-task or external `pkill` — **REFUTED**
- No user crontab, no `/etc/cron.*/` job fires at 22:03.
- No systemd timer (system or user) is scheduled in that window.

### 4. tmux server itself crashed/restarted — **REFUTED**
- `maw-tmux.service` Main PID is still 247 with start time
  2026-05-19 22:20:12. No restart event in `journalctl --user-unit
  maw-tmux`.

### 5. Host backup / snapshot / freeze coinciding with 22:03 — **REFUTED**
- `pvenode task list` on the PVE host shows the most recent vzdump and
  qmsnapshot/qmdelsnapshot tasks were at 2026-05-21 **02:00**, twenty
  hours before the incident. Nothing PVE-initiated ran at 22:03.
- `journalctl -u pve-container@112` for 22:00–22:10: no entries.

### 6. Shared `~/.claude.json` rewritten by a new spawn — **ROOT CAUSE (high confidence)**
Filesystem mtimes from the death window are the smoking gun:

| Path | Mtime | Notes |
|---|---|---|
| `/home/maw/.claude.json` | **22:03:15.315** | the canonical claude-code user-global config |
| `/home/maw/` (the home dir itself) | 22:03:15.317 | inode mtime bumped by an atomic rename of `.claude.json.tmp` → `.claude.json` |
| `~/.claude/backups/.claude.json.backup.1779393763354` | 22:02:44 | claude-code's own automatic pre-rewrite backup; the suffix is the unix-ms timestamp of when the backup was taken |
| `~/.claude/sessions/`, `~/.claude/shell-snapshots/` | 22:03:14.95 | claude internal state dirs touched ~360 ms before the rename |
| All six dying agents' `~/.claude/projects/<encoded-cwd>/*.jsonl` | 22:03 | each agent flushed its session log moments before dying |

Mechanism:

1. claude-code stores **all** per-user state in one global file —
   `~/.claude.json` — and the entire `~/.claude/` tree is shared across
   every CLI instance running as the same OS user.
2. When MAW spawned the 7th agent (the polyrepo task) at 22:03:15, that
   new CLI did the standard claude-code startup: read `.claude.json`,
   write a timestamped backup into `~/.claude/backups/`, write a fresh
   `.claude.json.tmp`, and `rename(2)` it over the live file.
3. The other six already-running claude-code processes had the *old*
   inode open / cached. When their next config refresh (or session-list
   reconcile, or watcher tick) noticed the file had been replaced — or
   they themselves attempted a write that lost the race — they exited.
   This precisely matches what we see: simultaneous deaths, no OOM, no
   signal from MAW, no kernel events, tmux server unaffected.
4. The temporal coincidence we noticed earlier ("new spawn happens in the
   same JS tick as the mass-death") was not a coincidence at all — the
   spawn **is** the cause.

This also explains why this has happened *twice*: any time MAW spawns a
new claude-code agent while ≥1 others are already running, the new one
clobbers shared config and the running ones can die.

The leftover orphan `fifo-test-*` `sh` probes are an unrelated leak
(noted in §B-5); they survived for the boring reason that they don't
touch `~/.claude.json` at all.

## What to do next

### A. Fix the root cause: give every agent its own claude-code config dir

This change stops the bleeding. §B and §C below are observability and
defense-in-depth; without §A the same incident will recur the next time
a claude-code agent is spawned while ≥1 others are running.

**Goal:** each spawned claude-code CLI must read and write to an
isolated config tree, so one agent's startup cannot rewrite another's
live `.claude.json`.

**Approach:** inject `CLAUDE_CONFIG_DIR=<per-agent path>` into the env
of each claude-code agent at spawn. (Per-agent `$HOME` is the obvious
alternative but drags every other tool — git, ssh, gh — into the
isolation and forces symlinks back; the env var is surgical.)

**Pre-implementation check (must do first):** confirm claude-code in
the version we ship still honours `CLAUDE_CONFIG_DIR`. Run
`claude --help 2>&1 | grep -i config` and a one-shot test:
`CLAUDE_CONFIG_DIR=/tmp/cc-isolate-test claude --version && ls -la
/tmp/cc-isolate-test`. If a `.claude.json` lands in that dir, we're
good; otherwise we fall back to per-agent `$HOME`.

**Concrete plan:**

a. In [src/lib/server/agents/AgentSupervisor.ts:655](src/lib/server/agents/AgentSupervisor.ts)
   — the existing env merge — add, gated on
   `role.cli_kind === 'claude-code'`:
   ```ts
   if (role.cli_kind === 'claude-code') {
     const cfgDir = `${cfg.dataDir}/agents/${agentId}/claude`;
     mkdirSync(cfgDir, { recursive: true });
     // Seed (copy, do not symlink — we need write isolation):
     for (const f of ['CLAUDE.md', 'settings.json', '.credentials.json']) {
       const src = `${homedir()}/.claude/${f}`;
       if (existsSync(src)) copyFileSync(src, `${cfgDir}/${f}`);
     }
     env.CLAUDE_CONFIG_DIR = cfgDir;
   }
   ```
   `Tmux.newSession` already accepts `opts.env` and serializes it into
   the spawn shell line ([TmuxSession.ts:88–122](src/lib/server/tmux/TmuxSession.ts:88)) —
   **no signature change needed**.

b. Pick a `cfg.dataDir`-rooted location so we benefit from the existing
   "everything maw owns lives under MAW_DATA_DIR" convention
   ([config.ts:44-45](src/lib/server/config.ts:44)). Suggested:
   `${cfg.dataDir}/agents/${agentId}/claude`. The agent's worktree is
   already a sibling under the same root.

c. **Cleanup**: when an agent is reaped/killed, `rm -rf` its config
   dir. Add this to `finishAsExited`
   ([AgentSupervisor.ts:429](src/lib/server/agents/AgentSupervisor.ts:429))
   and to `kill` ([AgentSupervisor.ts:709](src/lib/server/agents/AgentSupervisor.ts:709)).
   Gate on the agent being a claude-code kind.

d. **Update the JSONL-token reader to follow the per-agent dir.** This
   is the one secondary impact — [ClaudeJsonlTokens.ts:34](src/lib/server/agents/history/ClaudeJsonlTokens.ts:34)
   currently hard-codes `~/.claude/projects/<encoded-cwd>/`. Change it
   to accept a `configDir` argument and resolve
   `<configDir>/projects/<encoded-cwd>/<cliSessionId>.jsonl`. The agent
   row already has everything we need (the cwd is the worktree path;
   the session id is `agent.cli_session_id`). Don't try to be clever
   about backward-compatibility for already-archived agents — fall
   back to `~/.claude/projects/` if the per-agent path is missing, so
   the archive page keeps working for pre-fix agents.

e. **Leave `~/.claude/plans/` alone.** This is the user-global "saved
   plans" pool ([agentPlans.ts](src/lib/server/plans/agentPlans.ts)),
   not per-agent runtime state. No change needed; agents pick it up
   read-only.

f. **Migration note:** agents already running on a service that gets
   upgraded keep using the shared config (they were spawned before the
   change). They are not affected until they exit and are re-spawned.
   Worth a one-line note in the PR description.

**Verification for §A:**

- Spawn agents A and B back-to-back. Confirm each has a distinct
  `${dataDir}/agents/<id>/claude/.claude.json` after a few seconds.
- Spawn agent C while A and B are mid-task. **A and B must remain
  alive.** Today this kills A and B.
- `stat -c '%y %n' ~/.claude.json` before any spawn and after several
  spawns: mtime must not move under the new code. (Today it moves on
  every spawn.)
- Archive-page token totals still render for the new agents
  (regression check on §A-d).

### B. Make the next incident self-diagnosing (code changes — still worth doing)

Independent of §A. The root cause is now known, but the silence in
`journalctl` while six agents were dying is its own problem: we should
not need to read filesystem mtimes to know an agent died. The DB schema
already has the columns we need but they are not populated.
Specifically `agent_runs.exit_code` and `agent_runs.reason` exist in
[migrations/001_init.sql:110-123](migrations/001_init.sql:110) and
`closeAgentRun()` is defined in
[src/lib/server/db/queries.ts:730-739](src/lib/server/db/queries.ts:730) but
never called.

Changes to make (separate, small PRs — none of these need to ship
together):

1. **Capture exit signal / exit code per agent**
   - In [TmuxSession.newSession:88](src/lib/server/tmux/TmuxSession.ts:88),
     the spawn shell-line is already
     `cd <cwd> && exec env … <cmd> <args>`. Drop the `exec` (which
     replaces the shell, leaving no opportunity to inspect `$?`) and
     instead use:
     `cd <cwd> && env … <cmd> <args>; ec=$?; printf "%s\n" "$ec" > <agent-data>/exit; exit $ec`
   - Read that file in `finishAsExited()` at
     [AgentSupervisor.ts:429](src/lib/server/agents/AgentSupervisor.ts:429)
     and call `closeAgentRun(runId, ended_at, exit_code, reason)` —
     the helper already exists at
     [queries.ts:779](src/lib/server/db/queries.ts:779) with full unit
     tests. Today `insertAgentRun` is called on spawn but no matching
     close, so the column sits NULL for every run.

2. **Log every state transition**
   - Add a single `console.info('[AgentSupervisor] exited <id> reason=<r>
     ranFor=<s>s sessionAlive=<bool>')` in `finishAsExited` so that a
     mass-death event shows up in `journalctl` as 6 explicit lines, not
     as silence punctuated by 6 incidental commit-snapshot lines.

3. **Sample agent RSS periodically**
   - Hook a 30 s interval inside `AgentRuntime` that reads the pane's
     PID via `tmux display -p -t <session> '#{pane_pid}'` and then
     `/proc/<pid>/status` (VmRSS). Store the last sample on the runtime
     and flush it to `agent_runs.peak_rss_kb` on exit. Cheap and lets us
     answer "was this OOM?" instantly next time.

4. **Persist a tail of the terminal output on death**
   - When `finishAsExited` runs, snapshot the last ~50 KiB of the FIFO
     into `runtime_logs/<agentId>.tail` before closing it. Today the
     output is fan-out only — there is no postmortem to read. That tail
     alone will usually disambiguate "API auth error" vs "OOM" vs
     "killed by signal".

5. **Clean up the orphan `fifo-test-*` probes**
   - The two surviving sh processes from 21:48 / 21:51 indicate a leak
     in whatever code is writing `fifo-test-<pid>` paths against the
     production `-L maw` socket. The only `fifo-test-` references in
     the repo are in
     [src/lib/server/tmux/FifoStreamer.test.ts](src/lib/server/tmux/FifoStreamer.test.ts) —
     a test was run against the production socket (likely while
     iterating on FifoStreamer locally over the SSH session).
   - Action: gate the test harness's tmux socket name behind an env
     var, never `-L maw` by default. Audit any other test reaching the
     production socket. Kill the two existing orphans by hand
     (`kill 163123 163748`).

### C. Defense-in-depth (small ops changes)

These are *not* the root cause but reduce the blast radius and remove
ambiguity if OOM ever does occur:

1. **Enable `MemoryAccounting=yes` on both units** (`maw.service` and
   `maw-tmux.service` under [deploy/systemd/](deploy/systemd/)). Free,
   gives us per-unit `peak` accurately in `systemctl status`.
2. **Optionally set `MemoryHigh=6G` on `maw-tmux.service`** to start
   reclaiming page cache before any hard limit kicks in. Do **not** set
   `MemoryMax=` until we have telemetry — a hard cap could turn a
   recoverable spike into a real OOM.
3. **Lower `oom_score_adj` of the maw node service** and raise it on
   the tmux pane shells so that if the host ever does decide to kill
   *something*, individual agents go before the supervisor.
4. **Add a small swap file** (e.g. 2 GiB) inside the container. With
   `vm.swappiness=10` this becomes a buffer that prevents the kernel
   from having to choose victims at all under transient bursts.

### D. Verification

For §A (the root-cause fix):

- Spawn agents A and B back to back. While both are mid-task, spawn
  agent C. **All three should remain alive.** Today, C's spawn would
  kill A and B.
- `stat -c '%y %n' ~/.claude.json` before and after a spawn: mtime must
  not move under the new code.
- `find <maw-data>/agents -name .claude.json -printf '%T@ %p\n'`: one
  per agent, all with distinct mtimes.

For §B (observability changes), once §B-1 and §B-2 land:
- Trigger a controlled kill: from inside the container, `kill -9
  $(tmux -L maw display -p -t <agent> '#{pane_pid}')`. Confirm the
  journal records the exit with a non-zero exit code and signal.
- Trigger a controlled clean exit: type `/exit` inside a claude pane.
  Confirm exit_code = 0 is recorded.

For §C (defense-in-depth), `systemctl --user show maw-tmux.service | grep
Memory` should show real accounting numbers; the `peak` value in
`systemctl --user status` should match what the Proxmox dashboard
reports.

## Postscript — why did this only start on 2026-05-21?

The user (correctly) pushed back on an earlier hypothesis that MAW's
queue/scheduler (`feat(queue): add native queue + scheduler for
batch-planned agent spawns`, 2026-05-15) was the trigger. The observed
condition is **a single new spawn killing N already-running
long-running agents** — no batching needed. The user reports running
that exact pattern (manual spawn while agents are alive) for weeks
without trouble before 2026-05-21. The queue is at most a secondary
amplifier (more spawns ⇒ more race exposure when the race exists), but
not the proximate cause.

The real trigger is **a behavior change inside the `claude` binary
itself**, landing in version **2.1.146** (installed on the maw host at
2026-05-21 03:55 UTC, ~18 hours before the first observed mass-death
at 22:03 UTC the same calendar day). Evidence:

- `~/.local/share/claude/versions/` on the host shows
  `2.1.146 [Modify 2026-05-21 03:55]`, `2.1.147 [23:17]`,
  `2.1.148 [2026-05-22 07:15]`. The installer GCs older versions, so
  the pre-2.1.146 binary is gone — we can't diff it.
- `~/.bash_history` shows three `claude update` invocations across
  this window.
- `~/.claude/backups/.claude.json.backup.1779393763354` (2026-05-21
  22:02:44 UTC, 31 s before the first mass-death) is the oldest
  backup file present and matches the moment the new agent's startup
  began rewriting the user-global config.

Claude Code's public changelog (`https://code.claude.com/docs/en/changelog.md`)
has **no entry for 2.1.146** — it appears to have been skipped or was
internal-only. The nearest mechanical fingerprints in surrounding
releases are:

- **v2.1.140**: "Fixed settings hot-reload" — confirms a hot-reload /
  file-watch mechanism exists on settings files. If that mechanism
  extended to `~/.claude.json` in 2.1.146, a running CLI watching the
  file would see the inode swap from another CLI's startup rewrite
  and exit — exactly the symptom.
- **v2.1.141**: "Fixed IDE shell-integration lock files not respecting
  `CLAUDE_CONFIG_DIR`" — proves `CLAUDE_CONFIG_DIR` is treated
  internally as the isolation root.
- **v2.1.133**: "Fixed ECOMPROMISED when a history or session-log
  file lock is compromised" — there is a lock-file "compromised →
  exit" path that, if widened in 2.1.146 to cover `.claude.json`,
  would also produce the symptom.

We cannot pin the change to a specific commit/PR without claude-code's
source or an Anthropic-side disclosure. Confidence is medium: the
version-and-symptom correlation is tight (same calendar day as the
upgrade; no prior incidents in weeks of similar usage), but no
smoking-gun changelog line exists.

**Aside on the fix:** `CLAUDE_CONFIG_DIR` is **real but not officially
documented** as a user-facing isolation mechanism — it surfaces only
inside changelog fix descriptions (e.g. v2.1.132, v2.1.141), not in
the published env-var reference. Our fix relies on an
observably-supported but unofficially-documented escape hatch. Future
claude-code versions could change or remove it without notice, so the
fix is correct-for-now, not future-proof. If long-term stability of
the isolation matters, filing a feature request to formalise
`CLAUDE_CONFIG_DIR` would be worth doing.

## Follow-up — incident #3 (2026-05-22)

Same fingerprint, third occurrence. §A's `CLAUDE_CONFIG_DIR` fix
worked for agent spawns but not for the live integration test, which
spawns `claude` outside `AgentSupervisor` and runs against the
production `-L maw` tmux socket. §B-5's "gate the test harness's tmux
socket name behind an env var, never `-L maw` by default"
recommendation was never implemented and the test's `afterEach`
mass-killed every `maw-agent-*` session.

Closed in
[docs/plans/v0.3-mass-agent-death-3-pnpm-test-integration-kills-production-ag.md](v0.3-mass-agent-death-3-pnpm-test-integration-kills-production-ag.md):
the integration test now sets its own `CLAUDE_CONFIG_DIR` (Layer A) and
runs against a per-pid tmux socket via the new `MAW_TMUX_SOCKET` env
hook in `TmuxSession.ts` (Layer B); refuses to start when
`maw.service` is active or any `maw-agent-*` is on `-L maw` (Layer C);
and only kills sessions it spawned itself (Layer D).
